# claude-plugins

Source of truth for the `50arms` marketplace (`50arms/claude-marketplace`, install `danxbot@50arms`). Its plugins reach every Claude Code session on this machine and danxbot's container workers (through danxbot's catalog).

## The mantra is the one home for every rule it states (PLN-11 R-22)

`danxbot/mantra.md` is the mantra's single hand-maintained text: danxbot seeds the reminder
registry row `mantra` from it, and every agent receives that row's effective text (or the
board's override of it, DX-4144), never a copy:

- the main session: the module's `classic.SessionStart` hook (`danxbot/hooks/register.tsx`, source
  `startup|resume|compact`), ONLY once the session is signed in (DX-5554; before it, DX-3421
  gated it on a connected plan): a session with no dashboard key gets no danxbot text at all, at
  session start, resume or compaction, not even a one-line nudge; the trigger to sign in is
  `danxbot:plan-workflow`'s own skill description, not a hook line. Signed in, on a plan or not,
  the hook asks danxbot (`danxbot_api` on the session's own server) for the
  EFFECTIVE text of one of four events (`session_start` | `session_resume` |
  `after_compaction` | `sub_agent_start`, `GET /api/reminders/event/:event`) — the mantra
  (plan override, else the session's board override, else the row) followed by that event's
  own short lines, never a hand-typed duplicate of the mantra body. The dashboard decides the lines
  (DX-5554): a plan-connected session's text ends with the plan-only line, a session on no plan's
  carries the agent-scoped lines alone;
- every sub-agent, any type or plugin, of a signed-in session (DX-3384 final sweep widened this
  from `danxbot:worker-*` only; DX-5554 widened DX-3421's "plan-connected" gate to "signed in" —
  a sub-agent of a session with no key gets nothing): the module's `classic.SubagentStart` hook
  (additionalContext), event `sub_agent_start`;
- every dispatched worker: its profile's `{{reminder:mantra}}`, resolved by danxbot per
  dispatch against the card's board (DX-4144: one mantra; the dispatch fork is gone).

`mantra.md` is the git source `resolveReminderSeedItems` derives the `mantra`
registry row's default from at dashboard-seed time — it is NOT a runtime fallback any more
(DX-3421: a registry fetch failure is one line naming the failure and telling the agent
to tell the operator; the hook never re-reads this file). **Nothing else restates a mantra
rule** — no `SKILL.md`, agent body, hook text, `CLAUDE.md`, rule file or profile. A skill may
point at the mantra or add procedure the mantra doesn't state. To change a rule, edit
`mantra.md` and publish; phrase each rule so it holds for every one of those readers. No
prose states how many sub-agents to run (R-23).

## The time stamp, the event text and the restart notice are function hooks (DX-4234)

`danxbot/hooks/register.tsx` hands the model three things, each a hook of the module and none a script. The pure parts are `danxbot/hooks/context/*`; every `$` call stays in `register.tsx`.

- **Time stamp** (`context/stamp.ts`): `prompt.submit` and `tool.call` (every call that is not denied) add `MM/DD/YYYY HH:MM:SS ±HH:MM +Δ` to `context`; the date only on the first stamp or a new local day. The last stamp is `$.state` `lastStamp`. Operator decision PBLM-1915: both on every prompt and after every tool call.
- **Event text** (`context/events.ts`): a session start (`startup`, `resume`, `compact`) and `classic.SubagentStart` add the registry's `GET /api/reminders/event/:event` text for every session `GET /api/plans` finds signed in, on a plan or not (DX-5554; a registered session on no plan is a `session` row whose `plan_id` is null). A session on no plan's start or resume then also asks the restart notice, told after its event text. The compaction briefing follows only a plan-connected session's text. A failed fetch is ONE warning line naming the event and the reason; a signed-out or revoked session, one the MCP's agent gate holds (no team agent yet, or released at a resume: the dashboard's 403 `{state, instruction}` on the model's first dashboard call tells the model, since no `plan_connect` ran in the new process), and a plugin server that never connects are quiet; a failed plan read is a line only for a session whose connection record is on disk. A session start first polls `$.tool.list()` for the plugin's own `danxbot_api` (up to `STALE_GRACE_MS`; the old standby server never waits), then ONE deadline (`CONTEXT_DEADLINE_MS`, 8 s) covers all the reads of the start or of a sub-agent start together and answers a timeout line when it passes.
- **When a session start is told**: the engine has not bound the session when `classic.SessionStart` runs (desktop/headless startup, resume, fork), so `$.mcp.call` and `$.tool.list` throw there. That hook records `{sessionId, source, transcriptPath, predecessorId}` in `$.state` `pendingStart` (and, for a `compact` start while no main turn runs, detaches the resume prompt, below); the next `prompt.submit` or main-loop `tool.call` result (never a sub-agent's) takes it once and adds the event text and restart notice to `context`. `classic.SubagentStart` runs bound and adds its text to `additionalContext`.
- **Restart notice**: a session that is not on a plan (or has no key yet), on `startup`, `resume` or `clear`, calls the danx-dashboard server's `restart_notice` tool (it works before sign-in and runs its own 8 s deadline) and says its `{notice}`. Arguments by source (`restartAsk`): `startup` none (the server scans the project); `resume`, which a desktop fork reports too, `transcript_path` (the server finds the ancestor in the transcript's copied prefix); `clear` `predecessor_id`, the session id the `session.end` hook saw end (`$.state` `endedSession`), and only when that session held a connection record (it was on a plan; any other `/clear` is quiet and asks nothing). A resume missing its transcript path is a warning line, never a project scan. `{notice: null}` is quiet; a `{stopped: {reason, detail, fix}}` answer, an error result, a rejected call or a malformed answer is ONE warning line, never quiet. The server finds the earlier session; the plugin reads no connection record.
- Every dashboard call goes through the session's own server (`$.mcp.call`), never a spawn of the `danx-dashboard-mcp` CLI. `scripts/measure-injection.mjs` measures the stamp by running its pure `stamp`; the event text is the registry's and has no offline text to count.

## The session's team agent (DX-5554)

- **The band** names the team agent the session signs in as and what it holds, read from the `GET /api/plans` answer's `session` row (`agent` {id, name} or null, `card_id` / `card_title`; a row that has neither shape fails the load, `hooks/plan/agent.ts`): `Tendai · PLAN-23 · name` on a plan, `Tendai · DX-77 · title` holding a stand-alone card (its Open link goes to the card's `/board/<id>` page and the footer reads `Danxbot · DX-77`), `Danxbot · Tendai: not connected to a plan or card` on neither. The avatar is neither read nor drawn: the terminal's `Image` takes bytes the module cannot fetch, and the desktop has no image element for a URL.
- **The agent gate** (danxbot `packages/danx-dashboard-mcp/src/agent-gate.ts`): after `plan_connect` answered `agent_needed` or `agent_limit_reached`, the MCP answers every other dashboard call with that block as an error result. The plan load reads it as a ready view with `agentBlock` set (`Danxbot: waiting for a team agent`), never Disconnected, so the relay keeps running on no plan: the dashboard's wake once a person created the agent arrives through it.
- **Release at session end:** `session.end` calls `DELETE /api/plan-sessions/me/agent` through `api()` only when the process really ends (`prompt_input_exit`, `logout`, `other`); a `/clear` or `/resume` keeps the agent, since the MCP carries on with the same session id. So the agent is free for the team at once instead of after the dashboard's 30-minute dead-session window. Bounded by `AGENT_RELEASE_DEADLINE_MS` (3 s); a failure is one toast; a signed-out or revoked session, or one the agent gate holds, asks nothing. Which session id the MCP sends on a `/clear`'s end is UNVERIFIED live. Tests: `danxbot/tests/agent-release.test.tsx`, `danxbot/tests/plan-agent-band.test.tsx`.

## The reports are function hooks (DX-4235)

`danxbot/hooks/register.tsx` also keeps the dashboard told what a plan-connected session is doing, so the dashboard can show the session's running work and nudge an idle one. Each report is a hook of the module and none a script. The pure parts are `danxbot/hooks/reports/*`; every `$` call stays in `register.tsx`. Every report goes through the session's own server (`$.mcp.call` of the plugin's `danxbot_api` tool). A report the dashboard does not take is a toast, never swallowed. What each report needs of the plan state the module holds (`$.state` `reports` remembers what was opened):

- Opening something (a sub-agent's row, a shell's row, a liveness re-post) needs the session known to be on a plan.
- Closing what was opened (a sub-agent's finish, a shell's end) is owed because its start was posted, so it goes out even while a plan refresh has failed and the view holds no plan for a moment. It is dropped only once the dashboard says the session is on no plan (or a person revoked its key): the dashboard takes no report from such a session. So before every leave or move to another plan the module takes part in (the band's Disconnect, the model's `plan_connect` leave or move to another plan, caught in `tool.call` before the call runs), every owed close is posted first, in one call bounded by `LEAVE_CLOSE_DEADLINE_MS` (3 s) so a dead dashboard never holds the leave; a failure is one toast naming what may stay running. A leave that then does not happen (refused, or the call failed) takes back what it can: closes the dashboard did not take are owed again, and closes it took stay forgotten, with one toast saying they read as finished while the work runs (the dashboard keeps a row's first finish, so a reopening post would change nothing). The module has no sign-out of its own.
- The count is kept true the same way: sent while the session is on a plan, and while the plan state is unknown if a count is on record.
- The ready-cards check runs unless the session is known to be on no plan; its own read asks the dashboard which plan the session is on.

The reports themselves:

- **Activity** (`POST /api/plan-sessions/me/activity`): a sub-agent's start at `classic.SubagentStart`; its end at `turn.complete` with an `agentId` (a clean end or a failed one); a background shell's start at `tool.call` when the call's result names a `backgroundTaskId`, labelled by the call's own `description` redacted (`hooks/reports/label.ts`, a port of danxbot's telemetry `redactLabel`/`labelOf`, pinned by that package's own cases in `tests/reports-label.test.tsx`; never the command); that shell's end at the first `classic.Stop` or `classic.SubagentStop` whose `background_tasks` no longer lists it as running. A running sub-agent's own tool calls re-post it as alive, at most once per 60 s.
- **Ready-cards check** (DX-4534): at a `classic.Stop` of the plan-connected main session that is not already a stop-hook continuation (`stop_hook_active`), it reads `GET /api/plans/mine`, then `GET /api/issues` for each board of the plan. When ready, unclaimed cards wait, it returns `{block: <reason>}`: up to 5 of them by name and one line saying what to do. A read that fails lets the stop happen; a signed-out session says nothing; any other failure is one toast.
- **Agent pause** (DX-4997 / DX-4951 / DX-5033; `hooks/reports/pause.ts`): a session with nothing to do tells the dashboard (`PUT /api/plan-sessions/me/pause`) and the dashboard holds its machine messages. The server ends the pause on any request carrying the session header to a card or plan route (the agent's own call), so EVERY `danxbot_api` call the plugin's hooks make goes through `api()` in `register.tsx`, which passes `background: true`: the MCP client (the `@thehammer/danx-dashboard-mcp` release of DX-5033 or later) turns it into the `x-danx-plugin-background: 1` header, and the dashboard keeps the session live for such a request without taking it as the agent acting. Never pass it on the agent's own calls, and never make a `danxbot_api` call from a hook except through `api()` (`d.unmarked` in the test kit must stay empty). The ready-cards check first reads `GET /api/plan-sessions/me/pause`. An unexpired agent pause: the Stop reminder allows the stop (and makes no card read). The plan-tab keepalive ignores the pause (DX-5093: it costs no model turn). A 404 whose body carries the stable `message_id` `issuesDb.sessionNeverRegistered` (never its English text) is a session with no pause (free, quiet); any other 404 (a plugin newer than the dashboard) behaves as not paused and is toasted once (`olderDashboardTold`); any other failed read is a skipped check (Stop) or a retried attempt (keepalive), never a guess. The plugin pins no MCP version (above), and a plugin never waits for the relay (DX-5314, "A plugin runs beside an older relay" below): a danxbot MCP from before the DX-5033 release refuses the unknown `background` key; that call is made once, never retried without the key (DX-5062), and fails with one sentence, `STALE_MCP_LINE` (`hooks/relay/refusal.ts`), that names the fix (restart the session) and is short enough to stay whole in every toast this failure reaches; `api()` marks it `sentence` so `errText` adds no `mcp:` before it, as for a classifier refusal.

## danxbot's hooks are one native module (DX-4232)

`danxbot/hooks/hooks.json` is `{"modules": ["./register.tsx"], "description": ...}` and has no `hooks` key: every hook the plugin has is a native function hook of that module (the plan band, `/danx-plan`, the relay, the stamp and event text, the reports). The engine loads a module whole or not at all, and `claude plugin validate` names a module that would fail to load, so no hook runs half-broken beside the others and a publish refuses a module that does not validate (below). `danxbot/scripts/` holds only the MCP server launcher (`dashboard-mcp-server.mjs` and `lib/dashboard-mcp-package.mjs`) and the screenshot tool (`capture-screenshot.mjs` and its `lib/` helpers); `danxbot/tests/plugin-modules.test.mjs` pins both.

- Code: `danxbot/hooks/register.tsx` holds everything that takes `$` (the engine follows `$` only into a function in the same file, and `$.state` atoms must be declared in the file that reads them); `danxbot/hooks/plan/*` is pure drawing, shaping and constants. The `$.state` contract is `danxbot/types/index.d.ts`, named by `plugin.json`'s `"types"`.
- Every control in the band that opens a page (the plan, the open-problem count, a problem, a card, the sign-in and permission approval pages) is a link inside a `Markdown` element (`hooks/plan/links.tsx`, `mdLink`), never a `Link` element and never a `Claude_Browser` tool call (DX-4630). A `Link` opens the external browser; a Markdown link with no `onLinkPress` takes the path a conversation link takes, in the app's in-app browser at once (proven live, desktop, CLI 2.1.286). The plugin opens no page itself on a press and keeps no browser tab for it; the one exception is the plan-tab keepalive's own look at the pane, run by a timer (DX-5093, below). A sign-in or permission request is drawn as its link and confirm code the moment it exists.
- **Plan-tab keepalive (DX-3900, DX-5093):** the desktop app disconnects a session's preview 1800 s after its last turn ended (`main.log`: `[WarmLifecycle:preview] Idle timeout reached`), so the keepalive runs only for a session the desktop app hosts, which is sticky (`desktopHosted`): the app starts its sessions headless (`session.start` has `surface: null` with `$.session.surfaces()` = `['desktop']`), detaches about 5 s later and attaches again only while the person views the session, so the surfaces at fire time say nothing. It is set at `session.start` when `surfaces()` lists the desktop or `CLAUDE_CODE_ENTRYPOINT` is `claude-desktop` (the app sets it on every process it spawns, so a resumed, never-viewed session still arms, DX-4806), and by any `session.attach` of the desktop; a terminal session (entrypoint `cli`, no desktop surface or attach) has no plan tab and is never looked at. It follows the plan CONNECTION, not the relay loop's health (`keepalivePlan`, set by `startRelay`, cleared on plan disconnect and process end). One `$.clock.after` timer (`hooks/relay/keepalive.ts` has the constants): an idle period starts at connection and at every main-loop `turn.complete`, a turn start cancels it.
  - **No model turn (DX-5093):** the hook looks at the desktop's Browser pane itself. The pane's server is one of the session's MCP servers (`Claude_Browser`, tools `mcp__Claude_Browser__*`) and `$.mcp.call` runs a tool of any connected server by name (claude.exe 2.1.295 looks the tool up in the session's tool list, so the app's SDK-hosted server answers like any other; `hooks/relay/browser.ts` has the pure parts). After `KEEPALIVE_IDLE_MS` (25 min) it calls `tabs_context`: a tab on the plan page's origin is held and nothing more is done; a closed pane is opened with `navigate` to the plan page; an open pane without that tab gets `tabs_create` (background) and `navigate` with the new `tabId`, so a page the person reads is never navigated away. The next look is an idle period (25 min) on, the cadence the keepalive always had, so a tab the person closes on purpose is not reopened more often than before. Whether a call to the pane counts as use to the app's 30-minute timer is UNVERIFIED live. It submits no prompt, reads no registry wording (the `tab_keepalive` event text is unused) and ignores the agent pause (a look costs nothing). A desktop-hosted, plan-connected session with no callable `Claude_Browser` server (the engine's "no connected MCP tool" rejection) is toasted ONCE per session (`browserMissingTold`, `$.state`) saying its plan tab will close and nothing reopens it, and is looked at again an idle period on; no prompt stands in for the pane, since a prompt could not tell whether the tab is missing. A `tabs_create` answer with `reused: true` is refused (it may be a tab the person holds). A failed attempt (the pane unreadable, `navigate` or `tabs_create` refused, the plan page not loaded) is toasted and retried every 60 s until 29 minutes after the turn ended, then gives up with a toast. A turn that starts after the app's 30 minutes had passed with no look (the computer slept) runs the same look at once (`recheckTab`).
  - The three pane tools are allowed by `ownServerCheck` (`tool.check`, like the plugin's own server, DX-4805) for a call this plugin raised only; the model's own call to them keeps the engine's verdict, and an engine `deny` or an organization `ask` ceiling stands.
- The plan event relay (the loop on the server's `plan_events_wait`) starts from a plan id, never only from a successful full plan load (DX-4233): `startRelay` is the one start, fed by the view, by a `plan_connect` answer's `body.session.planId`, and by `watchRelay`, a light read of `GET /api/plans?limit=1` that `session.start` repeats while the read fails (`RELAY_START_RETRY_MS`) and that a turn's end and a sub-agent's start or stop run when no loop does. At most one `watchRelay` read is out at a time; a failure of the watch is toasted once. The band says `events: relay not running` when the plan is connected and no loop runs.
- **The relay never awaits a delivery (DX-5398):** the poll loop (`relayLoop` / `handleAnswer`) only takes events from `plan_events_wait` and queues them (`queueEvents`) in the module `outbox` (`hooks/relay/outbox.ts`), then polls on at once from the newest cursor it took; heartbeats and the sub-agents' stats ride those polls, so they must never wait. A pump (`issueOutbox`, single-flight) issues the queued events in order, each as soon as the one before it has been *issued*, and `settleOutbox` stores the resume cursor per *delivered* event, in order; a refused event is issued again after the backoff (the band says `retrying`) and so can be delivered after later events (the cursor still never passes an undelivered one), and a failing cursor store halts the relay as the loop's own unexpected errors do (`haltRelay`). The reason: a plugin's `$.prompt.submit` does not settle when the prompt is queued behind a running turn but when the prompt ENTERS the session (claude.exe 2.1.299: the call returns a promise the prompt core settles at the idle), so a loop that awaited it was held for the rest of a main turn blocked in a foreground sub-agent (live evidence, DX-5398 note 16114). The outbox survives a replaced run of the same plan (the new run polls from `pollCursor`, so nothing in flight is asked for again or delivered twice; another plan's events are dropped, and the retrying failure of a dropped event with them). **The poll's cursor acknowledges:** the server drops every record at or below the cursor a `plan_events_wait` call presents (danxbot `plan-events-relay.ts`), and the loop presents the newest cursor it *took*, so a taken event that is not delivered yet exists nowhere but in the plugin. A reload of the hook module empties the module variable `outbox`, so every queued event is also written to the `relayOutbox` atom (`$.state`, declared in `types/index.d.ts`) before the poll that acknowledges it (`queueEvents` -> `persistOutbox`) and removed once delivered, after its cursor is stored; a run's start (`restoreOutbox`) rebuilds `outbox` from the atom when it is empty and issues what waits. A reload loses no event; it can repeat any event still in the atom (one issued and not yet delivered, including an urgent note already appended behind a waiting prompt): a duplicate, never a loss. A new process has no atom, and the server resumes from the stored (delivered) cursor. **Stall watch:** `checkRelayStall` runs every `RELAY_STALL_CHECK_MS`; a run whose loop made no step for `RELAY_STALL_MS` (it awaits a call that never settles: nothing it could say reaches anyone) gets a toast for the person and a note for the session (detached) and the relay is started again. The clock is the wall clock, so a tick that itself runs more than twice its interval late (`isLateTick`: the machine slept) is not judged and the count starts again from it. Tests: `plan-relay-outbox.test.tsx`; the kit's server drops records at or below a presented cursor as the real one does (`relay.server.dropped`), the kit has no second module instance so a reload is modelled as a fresh module with `seedState('relayOutbox', ...)`, and `holdPrompts()` models the engine's prompt (a submit that settles only on `release()`), and `relay.server.holdMs = 'timeout_ms'` makes a wait end as the server's does (a wait that never answers is a stalled loop, so a suite that moves the clock minutes sets it).
- **Auto permission mode and the plugin's own calls (DX-4805):** in auto mode the engine (2.1.293) puts a hook-initiated `$.mcp.call` through the same permission path as a model's tool call, ending at the auto mode classifier, and a call the classifier "gave no verdict" on is refused (`$.mcp.call(<server>, <tool>) refused: The server-side auto mode classifier gave no verdict for mcp__...`). That is despite the typed doc of `$.mcp.call` ("No permission prompt: the plugin's call ... is the grant"), and nothing in a plugin manifest ships a permission rule. So the module ships the permission as a `tool.check` hook (`ownServerCheck` in `hooks/relay/refusal.ts`, seated by `on('tool.check', ...)` in `register.tsx`): `allow` for a call whose `next.origin.plugin` is `danxbot` on a tool of its own server, but an engine `deny` or an organization `ask` ceiling always stands; the host sets the origin, so the model's own call to the same tool (origin `engine`) keeps the engine's verdict. UNVERIFIED live (needs a logged-in CLI in auto mode); the test kit cannot forge a plugin origin, so `plan-relay-refusal.test.tsx` pins the pure handler with a fake origin and `own-server-check-scan.test.mjs` pins that it is seated. If a refusal happens anyway it is never a quiet retry: the relay's wait is told once as `events delayed` and retried on the backoff, never halted (`classifyText` -> `refused`; DX-4982), the view shows one `blocked` state (the band's second line `BLOCKED_LINE`, label `Danxbot: blocked by auto mode`, never Disconnected / Sign in failed) that the next successful load replaces and that names the plan the model's own `plan_connect` answered (`modelPlan`, cleared by any loaded view, leave, /clear, resume or session start). The band's plan link is built by `blockedOrigin` (`hooks/plan/origin.ts`) from the load's origin (which `loadView` fills from the stored one), else `DANXBOT_DASHBOARD_URL`, else the plugin's `dashboard_url` option that the engine passes to `register`; no link is drawn when none of them is a valid origin. A refused first read of the relay start is told once (`tellRefusal`), and `api()` puts the fix into the error the view shows. The fix text is `CLASSIFIER_FIX`: an allow rule `mcp__plugin_danxbot_danx-dashboard__*` in `permissions.allow` of `~/.claude/settings.json` (or `/permissions`); the plugin then resumes on its own (restart the session only if it does not); updating the plugin does not help. The fix names the one-step route: `/danxbot:start` (step 2 of `skills/start/SKILL.md`) checks `~/.claude/settings.json`, explains why, and adds exactly that one entry only when the person says yes (an invalid settings file or a non-list `permissions.allow` is left untouched with the manual instruction; every other setting is kept); it applies without a restart (a restart only if the band still says blocked). The `plan-workflow` skill's Live events bullet names the same route. This is the documented workaround for any session whose relay never attaches in auto mode.
- The relay's failures are retries, not halts (DX-4233): "server not connected yet" and "no session is bound" retry on the backoff; only an answer that names the tool as unknown ends the plan's relay (old server). A "not connected" answer counts as that only after `OLD_SERVER_AFTER_FAILURES` failed waits in a row over `OLD_SERVER_AFTER_MS` (the 4th failure), each with `$.tool.list` showing the plugin server's other tools without `plan_events_wait`, and a fresh plan read saying the session is signed in and still on this run's plan (the tool list is dynamic: it changes at sign-in, a grant and a key loss). A session found signed out or on another plan then ends the run as the signed-out answer does.
- Every plan load answers within `LOAD_DEADLINE_MS` or is shown as an error (DX-4233); its refresh keeps the lock for up to `LOAD_ORPHAN_WAIT_MS` more (applying a late answer) so at most one load runs, and a lock held past `LOCK_STALE_MS` (their sum plus `LOCK_TAIL_MS`) is taken over.
- Tests: `danxbot/tests/plan-*.test.tsx` run under `claude plugin test danxbot` inside the test container (`npm test`, below; each over `['terminal','desktop']`), with the stand-in dashboard in `danxbot/tests/plan-kit.tsx`. A suite built on the kit imports `test` from `./plan-kit`, never from `claude-code/testing`: the kit's `test` gives each case a 60 s budget, because a long mocked-clock case pays real time per mocked minute and passes the runner's 5 s default under load (DX-4883). `claude plugin validate danxbot` is the loud check: in the desktop app a module that fails to load says nothing.
- `scripts/publish.sh` runs `claude plugin validate` for any target plugin whose `hooks.json` declares `modules`, and then the whole suite (`npm test`, below), before it bumps anything, and refuses the publish if either fails. **The validate step needs the `claude` CLI: it is not on PATH in this machine's Git Bash, so set `CLAUDE_BIN` to the executable** (for example the desktop app's `claude-code/<version>/<hash>/claude.exe`) or the publish is refused naming it. The suite runs its own CLI in the container (the version `.claude-code-version` pins, which `Dockerfile.test` installs). **Validated CLI (CAV-1, DX-4793, DX-4854, DX-5222): 2.1.299** (`claude plugin test danxbot` 1470/0 and `claude plugin validate danxbot` clean; the line before it was 2.1.295, then 2.1.293, then 2.1.288). Function hooks are an early-access API that changes between CLI releases: re-run both on every new desktop CLI, update `.claude-code-version` and this line. ## Tests run in ONE place: a Linux Docker container (DX-5648, operator 2026-10-21)

## The compaction handshake starts /compact on ready and holds automatic proposals, per agent (DX-5231, DX-5222)

`danxbot/hooks/register.tsx` (`startReadyCompaction`, `clearLeftoverArming`, `compactionVerdict`; pure part `hooks/compaction/control.ts`) runs an operator session's compaction handshake (DX-5231). **Start:** when the agent's ready is accepted the control file carries an unexpired release; at the next MAIN-loop `turn.complete` (never a sub-agent's, never inside a turn or a command hook), or at a 5 s idle check when the release lands after the turn already ended (the relay writes the file after the agent's call returned; the plugin gets no file-change event; the check reads a local file, never runs while a main turn runs, and is armed only while the control file carries a control, so a session with no handshake pays nothing and the check stops when the control goes), the plugin spends the release (once: one compare-and-set on the `claimedRelease` atom before any other await, so a turn end, an idle check and a person's `/compact` racing each other start it exactly once; kept in `$.store` afterwards) and queues `$.command.run({ command: 'compact' })`, which the host runs once the session is idle. Verified on Claude Code 2.1.299 in the desktop app (DX-5217 comment 15740: trigger `manual`, 549,668 to 11,259 tokens); `$.session.compact()` and `$.prompt.submit('/compact')` are refused in that host (the headless / SDK host, `--input-format stream-json`; only a terminal TUI accepts `$.session.compact()`). The control carries no instructions, so the command gets no arguments. **No arming FOR the main agent:** nothing is armed to make the main loop compact (its compaction is the plugin's own `/compact`); the only early-proposal variable is the sub-agents' (below), which also makes the main loop propose from the floor once it is set, and the gate holds that `auto` proposal while the session is under the handshake (a control file with a control), and passes it at `passAtTokens` (the safety valve), when it cannot read or size anything (fail open), or when the real window is smaller than the control assumed. A `manual` trigger (a person's `/compact`, or the plugin's own start) always passes, and spends a waiting release so the plugin runs no second `/compact`. **Never `CLAUDE_CODE_AUTO_COMPACT_WINDOW`**: Claude Code reads it as the window the context meter (`/context`) measures against, so a 1M session showed its floor as its maximum (DX-5217). A process an older plugin version armed still holds that variable, or the undocumented `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` (Claude Code's `testPctOverride`), after a plugin reload, so the first main-loop turn start or end clears both ONCE per process (the `leftoverArmingCleared` flag in `$.state`; a later writer, such as the sub-agent percent below, is never wiped) once the session has a control file (`$.env.set(name)` with no value restores the default at once, verified).

**Sub-agents (DX-5222)** have no command form that starts their compaction (`$.command.run` compacts the main session only), so the only compaction one can have is Claude Code's own automatic proposal, and the plugin arms it, recommends it and gates it per sub-agent:
- **Gate:** `on('session.compact', { trigger: /^(auto|precompute)$/ })` (`onSessionCompact`) judges every automatic proposal, and a `precompute` (the same compaction computed ahead of time) the same way but without spending a release or announcing anything (the compaction that follows is an `auto` proposal, judged then); the event names the proposing `agentId` (absent: the main agent, whose verdict is `compactionVerdict`, unchanged). A sub-agent with an `agents[id]` entry in the control file passes at that entry's `passAtTokens` or once on its own unexpired, unspent `releaseId` (spent per session AND agent in `$.store`, `usedReleaseKey(sessionId, agentId)`; a session's records prune together); one with no entry passes at the valve of ITS model line (`control.valves`, written by the dashboard from the board's model capabilities, the operator-session twin of the dispatch worker's `valves.json`, DX-5259). An unknown size, an unknown model or a line with no valve is `{skip}` and told once, never guessed (`agentVerdict`, pure, in `hooks/compaction/control.ts`); that is the one exception to the gate's fail-open rule. **The classic `PreCompact` gate and whether the host runs `session.compact` (DX-5365):** one answer, `hostRunsSessionCompact`, decides both this gate and the arming below: the `sessionCompactSeen` flag is up (the first `session.compact` event of any trigger raises it; `$.state`, so a module reload keeps it), OR the engine's release is 2.1.299 or later (`SESSION_COMPACT_FLOOR`, read once per process with `$.session.version().base` and kept in `$.state`; the runtime has no capability flag, and 2.1.299 is the one engine the per-agent gate was verified on; a release that cannot be read, because the call throws or names no `base`, is not known to run it, and the person is told once when the handshake would arm). Once it holds, the classic gate leaves an automatic proposal alone (core runs it beneath `session.compact`, which judged it per agent; the classic input cannot tell the agents apart). Otherwise, a host not known to run `session.compact` has only the classic gate, which holds every automatic proposal like the main agent (on a managed install neither the classic hook nor `session.compact` runs for a plugin a person installs, per `claude plugin validate`, so the handshake gates nothing there). Three kinds of proposal skip `session.compact` and reach only the classic hooks, so on a host that runs `session.compact` each passes the classic gate unjudged: a model whose window source is `auto` (under 1M in the catalog), the in-process runner, and an isolated `delegatedObservation` sub-agent (the built-in comment-thread-analyst). That is fail open, and it assumes the 1M models the handshake is built for (PLAN-42 caveat CAV-2): holding one by the MAIN agent's size would never release it, and its context is short-lived and bounded. The main agent's own proposals are still held at `session.compact`. `manual` is not matched by the `session.compact` gate; the classic gate answers it and spends a waiting ready.
- **Whose compaction the resume briefing follows (DX-5344):** Claude Code's classic `SessionStart` input names no agent (2.1.299: its `agent_id` is absent, as the classic `PreCompact` input's is). So `$.state` `compacting` keeps one entry per compacting agent (never one shared note, which parallel sub-agents would overwrite): a passed `auto` proposal at `session.compact` (`onSessionCompact`) enters its agent, a `manual` event enters the main agent, a `precompute` enters nobody. The entry settles by what core answers (`settledCompaction`): a result that is not a skip marks a sub-agent's entry `done`; a skip or a throw removes it; a sub-agent's stop removes it; an entry older than `COMPACTING_NOTE_TTL_MS` (10 min) is dropped. A `compact` restart (`restartBriefsMain`) records a pending start, and so briefs the main agent, when the main agent has an entry (consumed) or no agent has one (the unattributable kinds); a restart only sub-agents account for briefs nobody there. Each `done` sub-agent is told on its own first tool result (`takeAgentBriefing`, `subagentBriefingText`: its id, type and task, a pointer to its summary and progress notes, never the plan or cards), once and only on a plan-connected session, whichever restart came first. Residual risk (UNVERIFIED live): a compaction whose result never returns keeps its entry up to the age bound, and an unattributable restart in that window is read as that sub-agent's. The same holds while a sub-agent has finished compacting but has not yet made its next tool call. Rare case: when the main agent and a sub-agent compact together, the sub-agent's restart can use up the main entry, and if the main compaction then fails the main agent gets a stray briefing, and (DX-5385) when the main session is idle that consumed entry also starts a turn with the resume prompt.
- **The resume prompt (DX-5385):** a `compact` start that is the main agent's OWN (`restartBriefsMain` consumed the main agent's entry, which `session.compact` writes for every manual compaction) and arrives while no main turn runs (the plugin's own `/compact` after a ready, or a person's typed one) leaves nothing to carry the briefing, so `classic.SessionStart` detaches `resumeAfterCompaction`: if the session is on a plan (its connection record, `isPlanConnected`) it takes the pending start, renders it (the registry text plus the briefing, which opens with `RESUME_PROCEDURE` in `hooks/compaction/briefing.ts`: re-invoke the loaded skills, read the newest handoff agent note, re-read the In Progress cards, check the running sub-agents, continue the step) and starts the turn with it through `submitEvent` (the relay's one prompt path). The prompt is the only telling (the start is taken, so no second briefing on the next prompt or tool result). A start whose dashboard reads failed still carries the procedure after its warning line. A turn that began while the reads ran is the person's: the built briefing goes into that running turn as a note by the relay's one note path (`appendTrackedNote`, shared with `issueEvent`, which `deliverEvent` wraps, so a turn that ends with no tool result after it still tells the briefing once as a prompt), and no prompt queues; a refused note puts the start back for the next tool result. A prompt the session refuses is a toast and the start goes back. The `isRunning` read before the detach is a deliberate fast path: a running turn carries the briefing on its next tool result with no reads or take. A session not on a plan, a sub-agent's compaction and every other start source get none. **A restart with no entry at all** (the `restartBriefsMain` fallback: an unattributed sub-agent compaction such as a model under 1M, the in-process runner or a `delegatedObservation` sub-agent, or any host without `session.compact`, i.e. an engine older than 2.1.299) is briefed passively on the next prompt or tool result and NEVER starts a turn, since nothing proves the main agent was compacted; such a host never gets the resume prompt. `turn.start` and `turn.complete` of a sub-agent or fork (they carry an `agentId`) never touch the main loop's `turn` state, or `isRunning` could stick true. Tests: `danxbot/tests/compaction-resume.test.tsx`.
- **Size:** `session.compact` carries no token count and `$.session.usage()` is the main conversation's, so a streaming `turn.step` hook (`noteAgentStep`) records each sub-agent's last response (prompt tokens and model from the step's `usage`, `agentSizes`). A main-loop step never reaches the hook (the registration matches an `agentId`) and takes no slot; `AGENT_SIZES_KEEP` sub-agents are kept. The hook only observes (DX-5562): a wrong-form agent id (`subagentKey` throws) is told once and the step returns, never failing the sub-agent's request.
- **Recommendation:** `deliverAgentAsks` sends each running sub-agent's `agents[id].ask.text` with `$.session.send({ to: { agentId }, text })`, once per `ask.at` (`compaction-ask-sent:` in `$.store`; claimed first by one compare-and-set on the `claimedAsks` atom, like `claimedRelease`, so the 5 s check and a turn's sync never both send it, a failed send gives the claim back, and a claim is dropped with its delivered-request record when that record is pruned, DX-5562), at every sync, which includes the 5 s idle check while a main turn runs (only the compaction START waits for no turn). A failed send is not recorded and retried; a finished sub-agent is never sent to (a message would resume it). The main agent never receives one: its request is the relay's.
- **Arming:** `armSubAgents` sets `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` to the floor as a share of the window (`floorPercent`, two decimals rounded down) while the session is under the handshake AND `hostRunsSessionCompact` holds (an event seen, or an engine from 2.1.299: a fresh process arms at its first handshake sync, before any compaction; a host not known to run `session.compact` is never armed, since its classic gate alone would hold every agent; a variable set at runtime reaches a sub-agent already running, verified live, DX-5222 comment 16303), re-arms when the floor moves and takes it back when the handshake ends or the file cannot be read (an armed percent with nothing holding the proposals would compact every agent at the floor). The variable is process-wide, so the main loop proposes early too; the main gate holds it. `syncCompaction` runs `clearLeftoverArming` first, which raises `leftoverArmingCleared`, so the once-per-process clear can never wipe the armed value (DX-5222 comment 15880; pinned by `compaction-agents.test.tsx`).
- The control file is `{control: {..., agents, valves}}`. **A plugin runs beside an older relay (DX-5314):** a file with no `agents` or no `valves` (relay 0.1.311 writes neither, 0.1.315 to 0.1.317 only `agents`, 0.1.321 both) is NOT `bad`: `parseControlFile` returns the main-agent control whole with `subagents: null`, so the main handshake (recommendation, ready, the `/compact` start, the main gate, the main-agent idle check) works as before. While `subagents` is null: nothing is armed (`armedPercentOf` is null, and an armed percent is taken back), no ask is delivered, and a sub-agent's `session.compact` proposal PASSES (`agentVerdict` `subagents-off`, fail open: nothing is armed, so it only comes at Claude Code's own threshold, and refusing it would strand the agent at its window). The person sees ONE named notice (`RELAY_OLDER_NOTICE`, shown again if the file returns to whole and falls back): the dashboard MCP relay is older than the plugin, sub-agent compaction is off, reconnect the danxbot dashboard MCP server (`/mcp`) or start a new session. A field that is present but malformed is still `bad` (the generic unreadable toast, fail open): only an ABSENT field means an older relay.

Dispatches (containerised `claude -p`, no plugin) keep the percent variable and their own gate (DX-5230).

## A zeroed store file is recovered, never left to break every hook (DX-5577)

Claude Code keeps `$.store` as one JSON file per plugin (`~/.claude/plugins/store/danxbot_50arms-<hash>.json`) and writes it by temp file and rename. A write cut off before its data reached disk has twice left that file all NUL bytes. Measured on claude.exe 2.1.304: from then on EVERY `$.store` call (get, set, delete, keys) rejects with `HooksError: <plugin>@<marketplace>: store file <path> is malformed (JSON Parse error: ...)`, and the store API cannot repair it.

- Every `$.store` call in `danxbot/hooks/register.tsx` is made in `storeIo` and reached through `storeOp` (never a bare `$.store.x`). `storeOp` runs `danxbot/hooks/store/recover.ts`, which recovers that one error only: `$.fs.read` the file as bytes, keep it as base64 in `<name>.malformed-<ISO time, colons as dashes>.bak` beside it, write `{}`, one toast naming the backup, then run the call once more. State the plugin lost is rebuilt as on a fresh install. Any other store error, and a recovery that cannot keep the copy, is thrown to the caller. The match is on the host's own message, `<plugin>@<marketplace>: store file <path> is malformed (...)`, from the start of the message (`danxbot/hooks/store/malformed.ts`); bytes that already hold a JSON object are another process's reset and are left alone.
- The plugin test runner prefixes every refusal a fake hands to the plugin with `<plugin>: $.store.<op>: `, which the real program never does (the round-2 match anchored to that prefix passed its tests and never fired in a real session). So `danxbot/tests/store-malformed.test.tsx` drives `recover.ts` through its `StoreIo` with the host's message as measured, and the runner-level cases only pin that the wrapped form and other errors are not recovered. Never anchor the match to the runner's shape.

## The danxbot plugin carries no `@thehammer/danx-dashboard-mcp` version (DX-4321)

The version is the npm registry's `latest`, recorded in `${CLAUDE_PLUGIN_DATA}/dashboard-mcp/current`. The MCP server launcher (`danxbot/scripts/dashboard-mcp-server.mjs`, through `danxbot/scripts/lib/dashboard-mcp-package.mjs`) is the one thing that refreshes and installs it:

- Before it starts the server it refreshes the record in a detached child, and waits for that child up to `START_WAIT_MS` (22 s, under Claude Code's 30 s MCP start limit; `DASHBOARD_MCP_START_WAIT_MS` is the tests' seam). The child asks the registry for `latest`, installs it (node, no bash, no shell, into `${CLAUDE_PLUGIN_DATA}/dashboard-mcp/<version>/`; an install already there is skipped) and records it. A session started after a danxbot publish therefore runs that publish, with no plugin release (DX-5075: the refresh used to start only after the server, so the first session after a publish ran the version the previous refresh had recorded, one release behind; 0.1.300 predates the advisory dedupe by id and repeated a stored pacing message). The recorded version is installed first if it is not, and with no record the registry's answer is needed to start at all. The registry request is one added round trip on every start, plus the install on the first start after a publish.
- A refresh that settles in time with a new version starts that version. A refresh that fails, or is not done in `START_WAIT_MS`, starts the RECORDED version (installed first if it is not); an unfinished refresh goes on in the background, never restarting the running server, and the next start runs what it recorded.
- A refresh that fails keeps the recorded version and appends one line to `dashboard-mcp/refresh.log`; the next launcher prints that line to its stderr at its start (below).
- Old installs are pruned after the refresh, as a separate step with its own failure line (a prune that fails is never reported as a failed refresh): every staging directory and every version directory over an hour old, except the version this session runs, the recorded one, and any version a live process leases.
- Leases: every process that runs an installed version (the server launcher, and the detached refresh child, which leases the version its launcher ran) writes `<version>/.leases/<pid>` while it runs and removes it at exit, so another session's prune never removes a version a live session runs. A lease whose process is gone (a crash) holds nothing: every prune reads the leases of every version directory, kept and young ones included, and deletes the dead ones.
- **The refresh is a detached child (DX-5314, waited for by DX-5075).** The launcher starts it before the server (`node dashboard-mcp-server.mjs --run-refresh <recorded version>`, node only, no shell, `detached`, `unref`ed after the wait, ALL stdio ignored: it holds none of the launcher's pipes, because the MCP transport may wait for stderr to close) and exits when the server does, without waiting for it or stopping it. A refresh needs about 7 s, and the old in-launcher refresh was aborted silently by every launcher shorter than that (a 2 s probe), so `current` sat three versions behind while only short launchers ran. The child installs into its own staging directory (a fresh `.stage-*` per install), leases the version the launcher ran (`<version>/.leases/<child pid>`) while it works, prunes after it, and appends ONE line to `${CLAUDE_PLUGIN_DATA}/dashboard-mcp/refresh.log` when it fails, times out or is stopped (SIGINT / SIGTERM kill its npm and remove its stage; that clean stop is POSIX-only: on Windows a detached child gets a hard terminate, so its npm and stage are left to the next prune). The NEXT launcher prints the lines in that file to its stderr at start (the file is renamed away first, so none is lost or printed twice): a refresh is never silent, its failure surfaces at the next start. `DASHBOARD_MCP_NPM_CLI` is the tests' seam for npm's CLI (the child is a real process).

No plugin file carries a version literal of the package (a test scans for one).

### A plugin runs beside an older relay (DX-5314)

Claude Code hot-loads every new plugin version into every live session (it writes the session's pid into `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/.in_use/` within the same second for each live session, with no `/reload-plugins`), but a session's MCP relay keeps its version until its MCP server restarts (`/mcp` reconnect, or a new session). Publishing the MCP first, then deploying, then publishing the plugin therefore does NOT protect a live session: it runs the new plugin beside the old relay. DX-5314: plugin 0.15.36 required `valves` in the compaction control file, the sessions' relays (0.1.311 to 0.1.317) wrote none, and every live operator session lost the compaction handshake for hours with only a generic toast. The rule: **a plugin keeps working beside any older relay, degrading only the features the relay cannot feed, with a named notice** (what is off, why, and the fix: reconnect the danxbot dashboard MCP server or start a new session). Never read a field an older relay lacks as a corruption that disables a feature the older relay could feed; never fail the whole feature for it. Release order still helps new sessions (publish the MCP and deploy the dashboard before the plugin), but the plugin's own code must not depend on it.

## Publishing is TWO steps, and the second one is not optional

A plugin edit is not shipped until BOTH happen:

1. **Bump + push** — `./scripts/publish.sh <patch|minor|major> <plugin>`. The marketplace loader compares `version` fields, not commit shas; a plain `git push` of plugin source ships nothing to any consumer.
2. **Update this machine's installed records** — `update-claude-plugins` (symlink to `scripts/update-plugins.sh`).

Before any bump, `publish.sh` runs its pre-flights, in this order: the frontmatter lint, the general-audience scan, the hooks-module `claude plugin validate`, the whole suite (`npm test`: the node suites, which hold the rule scans such as `plan-relay-scan` (DX-5201), then `claude plugin test danxbot`, in the test container), and the injection budget. Any one failing refuses the publish with nothing bumped or pushed. The general-audience scan (`scripts/check-general-audience.mjs`) refuses the publish when a shipped skill, agent, hook, script string or the mantra names the author's own setup (a personal account or alias, the author's domain, a card or plan id, a repo path). It reads every shipped file, as its `listPluginFiles` lists them (what `git add <plugin>/` would commit, minus `tests/` and `node_modules/`), with comments in code excluded, and throws on a file type it does not know, so teach it a new type before shipping one.

Step 2 exists because **installed plugin versions are recorded PER PROJECT** in `~/.claude/plugins/installed_plugins.json`. Pushing a new version makes it *available*; nothing moves a project's record onto it. Claude Code's own auto-update cannot do it here: the desktop app launches its CLI with `DISABLE_AUTOUPDATER=1`, which the docs state disables automatic updates "for both Claude Code and all plugins".

The failure is silent and uneven, which is why it went unnoticed for two months: the `danxbot` project sat on `base` v0.3.15 (June 9) and `danxbot` v0.3.65 while the `platform` project on the same machine ran v0.3.27 and v0.3.113. Every session looked healthy while loading two-month-old skills, rules, and hooks.

## MANDATORY — run `update-claude-plugins` after ANY plugin push

`publish.sh` already calls it automatically after a successful push, so the normal flow needs no extra command. **Run it by hand whenever a plugin's content reached `origin/main` by any other route:**

- a plain `git push` of plugin source (no bump — fix that first, then update)
- a push from another machine, a dispatched worker, or the GitHub web UI
- a `git pull` that brought someone else's plugin bump into this machine's clone
- any time you are unsure whether this machine's records match `origin/main`

It updates **every plugin in every project on this machine** in one command — there is no per-repo invocation. It is idempotent and skips rows that are already current, so running it when nothing changed costs a few seconds and prints "already current". Running it unnecessarily is free; skipping it leaves projects silently stale.

```bash
update-claude-plugins            # sweep every project on this machine
update-claude-plugins --dry-run  # show what would be checked, change nothing
```

Updates apply to the NEXT session — a running session keeps the versions it loaded at launch. That is Claude Code's own model, not a limitation of the script.

A `SessionStart` hook in `~/.claude/settings.json` also runs it asynchronously with a 6h throttle. Treat that as a backstop, not the mechanism: as of 2026-08-13 the hook is wired but has NOT been observed firing.

## Mechanical pre-action check

Before declaring any plugin work done, answer both:

1. Did `./scripts/publish.sh <bump> <plugin>` run and push? No → the edit is unshipped.
2. Did `update-claude-plugins` run after that push (or did `publish.sh` run it for you)? No → this machine is still loading the old version.

"I'll update later" / "the consumer will pick it up" / "it's only a small edit" are the rationalizations both checks exist to block.

Both yes → done. **NEVER test, verify, or file AC or problems about the published version reaching or loading in a new session** (operator, 2026-09-27) — that is the Claude Code harness's job, it works, and it is not ours.

## Shipped files carry no card ids, source paths or internal mechanics (DX-5786, operator 2026-10-22)

Everything under `danxbot/` except `tests/` is installed on third-party machines and opened by their agents and people, who see their own cards and plans, the public dashboard API and the MCP tools, and nothing else. So a shipped file (skill, agent, mantra, hook, script, type declaration, manifest, and every comment in them) never names one of our card, plan or problem ids, a path or module in danxbot's / 50 Arms' own source, an internal profile or script, or an internal person or repo.

- **This overrides the issue-ref comment default** (`// CARD-ID: reason`) for shipped plugin files: a comment that needs a reason states the reason itself, in words. Card ids stay fine in commit messages, tests and this file.
- `scripts/check-general-audience.mjs` enforces the id and source-path parts over comments too (`publish.sh` runs it before any bump; `scripts/tests/check-general-audience.test.mjs` runs it over the shipped plugin). A failing line is reworded, never allow-listed.

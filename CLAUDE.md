# claude-plugins

Source of truth for the `50arms` marketplace (`50arms/claude-marketplace`, install `50arms@50arms`). Its plugins reach every Claude Code session on this machine and 50 Arms' container workers (through 50 Arms' catalog).

## The mantra is the one home for every rule it states (PLN-11 R-22)

The plugin ships no mantra text. Its default is the `mantra` row of the dashboard repo's own reminder seed
(`src/issues/reminders/seed.yaml`, in the dashboard repo), stored in 50 Arms' database and
overridable per install, board and plan. Every agent receives the reminder registry row `mantra`'s
effective text (or the board's override of it, DX-4144), never a copy:

- the main session: the module's `classic.SessionStart` hook (`50arms/hooks/register.tsx`, source
  `startup|resume|compact`), ONLY once the session is signed in (DX-5554; before it, DX-3421
  gated it on a connected plan): a session with no dashboard key gets no 50 Arms text at all, at
  session start, resume or compaction, not even a one-line nudge; the trigger to sign in is
  `50arms:plan-workflow`'s own skill description, not a hook line. Signed in, on a plan or not,
  the hook asks 50 Arms (`50arms_api` on the session's own server) for the
  EFFECTIVE text of one of four events (`session_start` | `session_resume` |
  `after_compaction` | `sub_agent_start`, `GET /api/reminders/event/:event`) — the mantra
  (plan override, else the session's board override, else the row) followed by that event's
  own short lines, never a hand-typed duplicate of the mantra body. The dashboard decides the lines
  (DX-5554): a plan-connected session's text ends with the plan-only line, a session on no plan's
  carries the agent-scoped lines alone;
- every sub-agent, any type or plugin, of a signed-in session (DX-3384 final sweep widened this
  from `50arms:worker-*` only; DX-5554 widened DX-3421's "plan-connected" gate to "signed in" —
  a sub-agent of a session with no key gets nothing): the module's `classic.SubagentStart` hook
  (additionalContext), event `sub_agent_start`;
- every dispatched worker: its profile's `{{reminder:mantra}}`, resolved by 50 Arms per
  dispatch against the card's board (DX-4144: one mantra; the dispatch fork is gone).

A registry fetch failure is one line naming the failure and telling the agent
to tell the operator (DX-3421); the hook never reads a local mantra file. **Nothing else restates a mantra
rule** — no `SKILL.md`, agent body, hook text, `CLAUDE.md`, rule file or profile. A skill may
point at the mantra or add procedure the mantra doesn't state. To change a rule, change the `mantra`
row in the dashboard repo's `src/issues/reminders/seed.yaml` (or override it in the app); phrase each rule so it
holds for every one of those readers. No prose states how many sub-agents to run (R-23).

## The time stamp, the event text and the restart notice are function hooks (DX-4234)

`50arms/hooks/register.tsx` hands the model three things, each a hook of the module and none a script. The pure parts are `50arms/hooks/context/*`; every `$` call stays in `register.tsx`.

- **Time stamp** (`context/stamp.ts`): `prompt.submit` (every prompt) and `tool.call` (a call that is not denied, and only when its agent's last stamp is `TOOL_STAMP_EVERY_MS` (60 s) old, or it has none: each agent, the main thread and every sub-agent, has its own entry in `$.state` `stampTold`, cleared at every session start and, for a sub-agent, at its stop) add `MM/DD/YYYY HH:MM:SS ±HH:MM +Δ` to `context`; the date only on the first stamp or a new local day, and `+Δ` counts from the last stamp sent (`$.state` `lastStamp`). A session start's first result always carries one. Operator decision PBLM-1915 put the stamp on both; DEC-308 (DX-6600, CP-52) ended the stamp after every tool call, because the lines between told the model nothing new and every later model call re-read each.
- **Finished sub-agent reminder** (`context/record.ts` `subagentDoneReminder`): a `classic.SubagentStop` only counts the stop (`$.state` `subagentsDone`); the MAIN session's next `tool.call` result (a call with no `agentId`, not denied) or its next prompt carries ONE reminder naming the count, which asks for each result as an agent note on its card in the same step as the next action. It used to be a message of its own (`$.session.append`), which cost the main session a turn per sub-agent (41 in one plan). The record is still owed, as CP-15 intended.
- **Event text** (`context/events.ts`): a session start (`startup`, `resume`, `compact`) and `classic.SubagentStart` add the registry's `GET /api/reminders/event/:event` text for every session `GET /api/plan-sessions/me` finds signed in, on a plan or not (DX-5554; a registered session on no plan is a `session` row whose `plan_id` is null). A session on no plan's start or resume then also asks the restart notice, told after its event text. The compaction briefing follows only a plan-connected session's text. A failed fetch is ONE warning line naming the event and the reason; a signed-out or revoked session, one the MCP's agent gate holds (no team agent yet, or released at a resume: the dashboard's 403 `{state, instruction}` on the model's first dashboard call tells the model, since no `session_connect` ran in the new process), and a plugin server that never connects are quiet; a failed plan read is a line only for a session whose connection record is on disk. A session start first polls `$.tool.list()` for the plugin's own `50arms_api` (up to `STALE_GRACE_MS`; the old standby server never waits), then ONE deadline (`CONTEXT_DEADLINE_MS`, 8 s) covers all the reads of the start or of a sub-agent start together and answers a timeout line when it passes.
- **When a session start is told**: the engine has not bound the session when `classic.SessionStart` runs (desktop/headless startup, resume, fork), so `$.mcp.call` and `$.tool.list` throw there. That hook records `{sessionId, source, transcriptPath, predecessorId}` in `$.state` `pendingStart` (and, for a `compact` start while no main turn runs, detaches the resume prompt, below); the next `prompt.submit` or main-loop `tool.call` result (never a sub-agent's) takes it once and adds the event text and restart notice to `context`. `classic.SubagentStart` runs bound and adds its text to `additionalContext`.
- **Restart notice**: a session that is not on a plan (or has no key yet), on `startup`, `resume` or `clear`, calls the dashboard server's `restart_notice` tool (it works before sign-in and runs its own 8 s deadline) and says its `{notice}`. Arguments by source (`restartAsk`): `startup` none (the server scans the project); `resume`, which a desktop fork reports too, `transcript_path` (the server finds the ancestor in the transcript's copied prefix); `clear` `predecessor_id`, the session id the `session.end` hook saw end (`$.state` `endedSession`), and only when that session held a connection record (it was on a plan; any other `/clear` is quiet and asks nothing). A resume missing its transcript path is a warning line, never a project scan. `{notice: null}` is quiet; a `{stopped: {reason, detail, fix}}` answer, an error result, a rejected call or a malformed answer is ONE warning line, never quiet. The server finds the earlier session; the plugin reads no connection record.
- Every dashboard call goes through the session's own server (`$.mcp.call`), never a spawn of the `platform-mcp` CLI. `scripts/measure-injection.mjs` measures the stamp by running its pure `stamp`; the event text is the registry's and has no offline text to count.
- **The dashboard server has two names (`DASHBOARD_SERVERS`, `hooks/plan/config.ts`):** `plugin:50arms:platform` in an operator session, and `platform` in a 50 Arms-dispatched agent, whose clean-room config (`--strict-mcp-config --mcp-config`) loads no plugin server; the plugin itself is enabled there only for the orchestrator profile. Only the usage-pacing calls (the spawn claim, its give-back, the line read; `pacingEnv` in `register.tsx`) ask the session which one it has (`liveServer`: the tool list, read afresh on every call, never remembered; `serverOf` in `hooks/plan/server.ts` picks the plugin's own when both are listed) and fall back to the plugin's name when neither is, so a session with no server is still refused (the strict cap). Everything else (`api()`'s default, the plan band, the relay, the permission poll, the `tool.call` matchers, `toolName`) is the plugin's server only: widening it would start the band, the relay and the permission poll inside dispatched agents, a product decision, not a fix. Test it with the kit's `servers` option (`tests/plan-kit.tsx`).

## The machine's disk notice (CP-1)

`hooks/register.tsx` also warns every session on an opted-in Windows dev machine when C: is under its free-space floor or a disk compaction window is open (`context/disk.ts` is pure; `diskLine` gathers the facts through `$`). It rides beside the time stamp on `prompt.submit` and on `tool.call` (sub-agents' included; `classic.SubagentStart` is plan-gated, so it is not used).

- **Opt-in:** a machine is warned only when `<Windows home>/.danxbot/` exists. Without it the plugin says nothing; with it and no `machine-disk-floors` file the notice is `DISK FLOORS UNAVAILABLE`. The limits come only from that file plus 50 Arms' two overrides (`DANXBOT_DISK_FLOOR_GIB`, `DANXBOT_DISK_HARD_MINIMUM_GIB`), checked against each other after the overrides.
- **Cost:** the Windows home is found once per session, a failure included (`$.state` `diskHome`): in WSL by listing `/mnt/c/Users` for a folder holding `.danxbot` (no interop call before the opt-in is known; `cmd.exe` and `wslpath` are asked only when several folders qualify); concurrent hooks share one lookup and one probe; the drive (`df` in WSL, PowerShell `DriveInfo` on Windows; `$` has no statfs) is measured at most once a minute (`diskMeasured`): a tool call answers from the last measurement and refreshes it in the background, a person's prompt measures before it answers. The notice is remembered per agent (`diskTold`) and repeated to the same agent only after 10 minutes or on a change.
- **Drive:** the Windows system drive (`SystemDrive` on Windows, `/mnt/c` in WSL), never the root of the home directory. Tests: `50arms/tests/disk-notice.test.mjs` (pure), `50arms/tests/disk-notice-hooks.test.tsx` (the hooks on the kit's fake host). Whether `tool.call` fires inside a sub-agent in a real session is UNVERIFIED live.

## The session's team agent (DX-5554)

- **The band** names the team agent the session signs in as and what it holds, read from the `GET /api/plan-sessions/me` answer's `session` row (`agent` {id, name} or null, `card_id` / `card_title`; a row that has neither shape fails the load, `hooks/plan/agent.ts`): `Tendai · PLAN-23 · name` on a plan, `Tendai · DX-77 · title` holding a stand-alone card (its Open link goes to the card's `/board/<id>` page and the footer reads `50 Arms · DX-77`), `50 Arms · Tendai: not connected to a plan or card` on neither. The avatar is neither read nor drawn: the terminal's `Image` takes bytes the module cannot fetch, and the desktop has no image element for a URL.
- **Two band buttons, two jobs:** Disconnect shows while the session holds a plan or a card and only leaves it (`session_connect` with `disconnect: true`): the session stays signed in with its team agent, the band offers no Sign in, and the model is told it holds nothing and joins again only when the person asks. Revoke shows whenever the session holds an agent, a plan or a card and only calls `POST /api/plan-sessions/me/person-disconnect` (it frees the agent and revokes the key; the next Sign in waits for a person): it makes no leave call. Neither runs while the other does, and both end the ready loop first. Neither button has a tooltip: `ButtonProps` in the host types has no such prop. A session holding a card draws that card's checklist progress as the plan donut (`GET /api/issues/<id>` with `fields {checklists: true}`; items with status `passing` over all items, none drawn for a card without items).
- **The agent gate** (the dashboard repo's `packages/platform-mcp/src/agent-gate.ts`): after `session_connect` answered `agent_needed` or `agent_limit_reached`, the MCP answers every other dashboard call with that block as an error result. The plan load reads it as a ready view with `agentBlock` set (`50 Arms: waiting for a team agent`), never Disconnected, so the relay keeps running on no plan: the dashboard's wake once a person created the agent arrives through it.
- **Release at session end:** `session.end` calls `DELETE /api/plan-sessions/me/agent` through `api()` only when the process really ends (`prompt_input_exit`, `logout`, `other`); a `/clear` or `/resume` keeps the agent, since the MCP carries on with the same session id. So the agent is free for the team at once instead of after the dashboard's 30-minute dead-session window. Bounded by `AGENT_RELEASE_DEADLINE_MS` (3 s); a failure is one toast; a signed-out or revoked session, or one the agent gate holds, asks nothing. Which session id the MCP sends on a `/clear`'s end is UNVERIFIED live. Tests: `50arms/tests/agent-release.test.tsx`, `50arms/tests/plan-agent-band.test.tsx`.
- **One connect tool (CP-83, DX-6917):** the MCP's `session_connect` is the one connect tool (the plan tool and the card tool it replaced are gone, with no alias). Its `target` is `PLAN-n` (a plan) or a card's id (a card on no plan); with none it only signs in and takes the team agent. `hooks/plan/target.ts` reads a target the way the dashboard does (`PLAN-` prefix = plan, any other text = card). `onSessionConnect` (`register.tsx`) runs the plan path (closes owed before a leave or move, the relay start, `modelPlan`) for a plan target or none, the card path (activity report, view refresh) for a card target, and the sign-in watch for every target; the band's Disconnect is the same tool with `disconnect: true` and the held plan's or card's `target` (`leaveCall`), never the old `DELETE /api/plan-sessions/me/card`. **A person's Revoke ends the session's sign-in (CP-89, DX-7026); a Disconnect does not:** Revoke calls `POST /api/plan-sessions/me/person-disconnect` (`PERSON_DISCONNECT_PATH`, answers `{released, revoked: true}`) and nothing else, and aborts any sign-in watch (`abortSignInWatch`), so the band never sits on `Signing in…`. The load then reads the revoked key (`key-revoked`: `access revoked by <owner>`, Sign in offered), the plugin makes no connect call of its own, `revokeNote` tells the model not to connect, and only the band's Sign in (`person_sign_in`, DX-6894) restarts the session. A Disconnect is the leave call alone: the session stays signed in with its agent and `disconnectNote` tells the model to join nothing until asked (see "Two band buttons" below). `DELETE /me/agent` stays the exit-time release. Tests: `50arms/tests/plan-disconnect-signin.test.tsx`, `plan-disconnect-hold.test.tsx`. The plugin names no MCP version (below): the registry's `latest` decides which MCP a session runs, so this plugin must be published right after `latest` moves to the first MCP that has `session_connect`.

## A toast is only for what nothing else on screen shows (CP-100, DEC-724)

- A sign-in request's or a permission request's Approve link and confirm code show in the band and never as a toast; the model is told the band shows them (`signInShownNote`, `permissionShownNote`). A person pressing Sign in while a request already waits does nothing: the band already draws it.
- A toast is kept only for an event with no other visual indicator (a failure, a refusal, a denied sign-in, the ready loop's reports). An outcome the band, the thread or the engine's own UI already shows (signed in, Disconnected, Revoked, signed out, access revoked, a request renewed, compaction starting) is no toast. A new toast names the event it is for and why nothing else shows it.

## The ready-agent loop (CP-43, PLAN-116 "The agent queue")

`/50arms:ready` (the `ready` skill's own command, which the engine runs as `50arms:ready` and the hooks module answers on `command.run` without the model; `hooks/ready/loop.ts` is the pure part, every `$` call is in `register.tsx`. The plugin registers no command named after one of its skills: the engine refuses it, and the throw ended `session.start` before the usage ticker started, CP-67) signs a session in, claims its team agent and joins the team's list of ready agents for the repo of its folder (`PUT /api/plan-sessions/me/ready`, dashboard DX-6610). `/50arms:ready off` leaves it. The command's join tells the model nothing (the skill's adds one line, see below): a sign-in or permission approval the loop raises goes through the band, and its outcome reaches only the loop. The server hands the session work; this loop keeps its place and clears it after a job.

- **The server owns the loop (DX-6692):** the dashboard keeps the session's ready loop on its row and answers it on `GET /api/plan-sessions/me` as `ready_loop: {repo, job: {kind, id} | null, ended} | null` (`serverLoopOf`; anything unreadable is told, never read as no loop). The band's load never shows such a fault: it carries it as the view's `readyLoopFault`, a session in the loop hears it from its own look, and a new process with no mark, which cannot tell whether it was in a loop, takes none up and says so once (`readyLoopUnread`). `ended` is the dashboard's one job-ended verdict (DEC-351). The plugin keeps no rule of its own for when a job has ended, and no job of its own.
- **The clear is a handshake (DEC-359):** once the job has ended, 50 Arms asks the model to wrap up and say ready. The ask reaches the model as the MCP's urgent session record, in 50 Arms' own words (it names the job and the route `POST /api/plan-sessions/me/clear-ready`), so the plugin adds nothing to it. Once the model has said ready, and while the job is still ended, the MCP writes the release into the session's clear file, `~/.config/danxbot/clear/<session id>.json` (`{v: 1, sessionId, control: {releaseId} | null, askedAt}`; `sessionFilePath` in `hooks/relay/session-file.ts` is the one layout of the MCP's per-session files, the compaction control and the `session_connect` record included). The file is named by the session's dashboard id, the row's `session_id`, never `$.session.id()`, which a `/clear` changes while the MCP keeps its id. `releaseOfClearFile` refuses a file written for another session, or one the MCP would not write (told once, nothing clears), and ignores `askedAt`. A release the row no longer judges ended (the file lagging a job that reopened) clears nothing.
- **The clear:** `$.command.run` of `clear` alone (DEC-392: a `/compact` first would only pay for a summary the `/clear` throws away), once per `releaseId`. The release is spent in `$.store` (`clearSpentKey`, pruned with the compaction's spent releases) only after the `/clear` proved itself by `$.session.id()` changing, so a failed `/clear` is retried and a spent one never runs again, in this process or the next. The rejoin is one `PUT /api/plan-sessions/me/ready {repo}`: the dashboard leaves the ended job the session still holds, as its own leave keeping the agent, and marks it ready, in one transaction. A rejoin that failed after the `/clear` is made again by the next look, with no second `/clear`. The clear does not start while a turn, a sub-agent or a background shell runs (`readyShells`, from `backgroundTaskId`, ended when a Stop's `background_tasks` no longer lists them; a toast says so, once). A `/clear` a Stop rejected (`remote-cancel`, or Claude Code's hold, `stoppedByPerson`) takes the session off the list. The fresh conversation is told `session_start`'s text (`loopReset`) on its next prompt or tool result. Measured on claude.exe 2.1.309 in the stream-json host the desktop app uses (CP-43 note 39907): `$.session.messages()` loses the conversation, `$.session.id()` changes, and the MCP server keeps its process and the id it booted with, so the dashboard sees one session.
- **The look:** `syncReady` is the one step, single-flight, run at the command, at every main-loop turn end and every `READY_TICK_MS`; nothing moves while a turn or a sub-agent runs. It reads the row (claiming an agent first when the hold gate answers), then the clear file, and then:
  - a release to run: it clears and rejoins;
  - a session whose dashboard loop has a job (on it, or past it with no work and no release yet): it waits, since the model wraps up in turns of its own;
  - a row with no work whose job the server says goes on: the server took that work while it was open (a card added to a plan, another session connecting while this one was quiet), so the session keeps its conversation, leaves the loop and says why (`readyWorkTaken`);
  - anything else: it marks, unless the mark stands. A session that holds work with no loop job (`/50arms:ready` run on a plan or card, or again after a Stop ended the loop) is marked nothing: the same `PUT` joins the dashboard's loop with that work as its job (DX-6697) and answers `{ready: null, ready_loop}` (`markAnswerOf`; anything else is told, never taken as a mark). The session then waits on that job as on one it was handed, and says so (`readyJoinedOnWork`).

  A look acts on nothing it read once a main-loop turn began after it started (`readyTurns`, checked by `lookGoesOn` after every call), since the model connects, leaves or says ready only in a turn; the look after that turn judges the session. A look held past `LOCK_STALE_MS` outside a clear waits on a call that has not settled, so the next trigger takes over, as the refresh lock does. The look taken over acts on no answer it gets after that, except a mark of its own that landed after the loop ended, which is taken back. One clear runs at a time, timed afresh when it ends.
- **Beside an older MCP server (the rule under "A plugin runs beside an older relay", DX-5314):** a server at 0.1.426 or older ignores the stream's `clear` frame, so 50 Arms' ask never reaches the model and no release is written. At every connect of the event stream the dashboard sends the compaction control, then the clear control, and every server the plugin serves writes the compaction file, a current one the clear file too, `control: null` included. So a compaction file with no clear file beside it (both under the row's `session_id`) is a stream that connected through an older server, whether or not the session holds work (`clearRelease`'s `olderSign`); no file at all is a stream not up yet, which says nothing. One look is not enough: at a session's first connect the dashboard writes the compaction frame, reads its database for the clear control, then writes the clear frame, so a look between the two finds a current server's compaction file alone. `clearRelease` reads the compaction file first and the clear file second (both frames landing between the reads read as a current server), and the loop tells `READY_RELAY_OLDER` only when the next look still finds the sign for the same `session_id` (`readyRelayOlderSeen`), once per process (what is off, why, and the fix: reconnect the server with `/mcp` or start a new session), and goes on, since a reconnect fixes it. A resumed session whose earlier process ran an older server keeps that compaction file, so two looks in the seconds before the new server's stream connects could still tell it once by mistake (UNVERIFIED live). `sessionFilePath` answers null for an id that is not plain (`[A-Za-z0-9_-]+`, the MCP's own rule), and each caller says what that means: no connection record, an unreadable compaction control, a clear file it cannot read.
- **Every exit ends the server's loop too:** `leaveReady` sends `DELETE /api/plan-sessions/me/ready`, the only way the dashboard's loop ends, on every exit: `/50arms:ready off`, a Stop, the band's Disconnect or Revoke, work taken, a refused mark, a failed sign-in or permission, a revoked key. Otherwise 50 Arms would later ask a session that left to clear.
- **The skill is the agent's own way on (CP-54, DEC-360):** `skills/ready/SKILL.md` is loaded by the agent whenever the person's work is 50 Arms work (yes by default, one question when unclear, off only for unrelated work). `onReadySkill` (a `tool.call` on `Skill`, main session only: a sub-agent's `agentId` never joins) runs the same `joinReady` as the command and adds the join line (`READY_JOINING`, or `READY_OFF` for the argument `off`) to the model's tool context. A resumed, signed-in session in no loop (this process's or its row's, and a row whose loop is readable) is told `READY_JUDGE_PROMPT` once after `adoptReadyMark` (`askReadyJudgement`, via `adoptThenAskReady`). The `ready-judged:<session id>` record in `$.store` keeps that once; `leaveReady` writes it last, so a person's `off` or Stop is never prompted again and a store failure cannot hold the server's loop.
- **Waiting:** each minute the session reads its row and writes the mark only when `session.ready` is gone, because every write tells every open tab of the team. A lost mark comes back with no person (a team-mate's claim clears a lapsed session's agent, and the mark goes with it). A session key with no agent is refused by the server's hold gate with a 403 (`agent_not_held`, `agent_needed`, `agent_limit_reached`) on the read and on the mark, before any route answers, and the background `POST /api/plan-sessions/me/agent` claims it again, with no person. Every call is `api()`'s background call, so waiting never counts as agent work and the key lapses after 24 hours with no exception (DX-5279); a lapsed key refreshes the view, so the band draws the approval link and Sign in.
- **Losing the agent:** a look the hold gate answers says nothing of the row, which keeps its work. So the loop claims, reads the row again and decides only from that. A claim that hands another agent to a session on a job that goes on tells the model the new name, once, from the last name a row showed (`agentName`), detached from the look. A job about to clear is told nothing.
- **Stop:** a main-loop `turn.complete` with `isAborted`, or a delivery refused with Claude Code's Stop words (`heldForInput`), leaves the list and the loop, says so in a toast, and ends the loop: only `/50arms:ready` (typed by the person, or loaded as the skill by the agent) starts it again, because Claude Code drops every plugin prompt until the person sends a message. A person pressing the band's Disconnect ends the loop the same way, and the session keeps its conversation. A person chatting with a waiting session is no job.
- **Claiming the agent:** the background `POST /api/plan-sessions/me/agent`, on every look that finds none. Once a `session_connect` found no agent, the MCP's own gate answers every other call with that until a later `session_connect` finds one. No timer calls it: only the look after a person's `/50arms:ready` does, once, through the sign-in watch (`claimAsked`), which also draws an approval it turns up. So a session refused that way does not join by itself when an agent frees: a person runs `/50arms:ready` again (DEC-350). `signInStep` reads a plan-less `session_connect`'s `state: agent_held` as signed in.
- **It reports by toast (DEC-366):** joined, left, a failure, a Stop. The band gains no line for the loop; only a sign-in's link and code stay there, as sign-in. `/50arms:ready off` or any leave takes the loop's own open approvals along: its sign-in watch ends and its permission request goes.
- **A refusal is not retried:** a `request_permission` refused, or a grant the list still refuses, each leave the list and say why. A mark the dashboard refuses does the same, once, unless the refusal is one the next look clears: the repo has gone, or the session holds no agent. A session that took work between the look and the mark is not refused: the mark joins it to the loop on that work, and so does a rejoin whose ended job reopened under the dashboard's lock (DX-6697).
- **Repo:** `git remote get-url origin`, then `GET /api/repos/<name>` (`cards.view`, which a session key has) for the two names the setup guide gives a repo, each checked by its `github_remote`, so the normal join needs no second approval. A repo registered under a name a person typed needs the team's list, `GET /api/repos`, read page by page, which needs `boards.view`: the loop asks a person once through the band's permission link, and a denied or expired request leaves the list and says why. No origin, another host or an unregistered repo leaves the loop and says why.
- **A restarted process** whose row still holds a mark, or whose dashboard loop is still recorded (a job taken, with no mark), takes the loop back up and says so (DEC-360: rejoining leans to yes). `adoptReadyMark` reads the view's `readyRepo`: the mark's repo, else the loop's. UNVERIFIED live.
- **Answers over the MCP's limit:** a `50arms_api` answer over 100,000 characters comes back as `reply_file` with no `body` (DX-4400). `textOutcome` names the file (`replyFile`); `api()` reads the body from it on every dashboard read the plugin makes (`wholeAnswer`), and `onAckCall` only for the model's own pickup (`isPickup`), the one answer of the model's whose body it needs (`connectedByPickup`). A file that cannot be read is a failure that names it.
- Tests: `50arms/tests/ready-loop.test.tsx`; the kit models the dashboard's `ready_loop`, the rejoin's leave and the clear file. ## The reports are function hooks (DX-4235)

`50arms/hooks/register.tsx` also keeps the dashboard told what a plan-connected session is doing, so the dashboard can show the session's running work and nudge an idle one. - Opening something (a sub-agent's row, a shell's row, a liveness re-post) needs the session known to be on a plan.

- The count is kept true the same way: sent while the session is on a plan, and while the plan state is unknown if a count is on record.

## The compaction handshake starts /compact on ready and holds automatic proposals, per agent (DX-5231, DX-5222)

**Mode (DX-7106, DX-6732, DEC-459).** The team's `compaction.mainSessionMode` reaches the plugin as `mode` (`compact` or `clear`). The dashboard sends it in the control of the session's stream (`OperatorCompactionControl.mode`), the MCP relay writes it into the compaction file (`fileOf`), and `parseControlFile` reads it into `GateControl.mode`. A file with no `mode` comes from a relay older than the setting and reads as `compact`; any other value makes the file `bad`.

With `clear`, `startReadyCompaction` runs `clearForCompaction` instead of `/compact`. It uses the same `clearCommand` as the ready loop's `runReset` (Claude Code's `/clear`, proved by `$.session.id()` changing), so there is no second clear mechanism. A `/compact` can run beside a working sub-agent, but a `/clear` would end its work, so the clear waits until no turn, sub-agent or background command (`readyShells`) runs. It waits before the release is spent, so the 5 s idle check retries while the release lasts. One `clearInProgress` flag, taken with no await between the decision and the flag, keeps the ready loop's released clear and a compaction by clear from ever running together; a compaction release that finds it held stays in the file for the next check.

The conversation the clear opens must resume, so the plugin marks the clear first. The `compactionClear` `$.state` atom covers a clear that keeps its process: it is carried across the clear like the ready loop's phase (so a reload of the module cannot lose it) and consumed by the one `classic.SessionStart` (source `clear`) the clear raises. A clear that ends the process (the desktop app) takes `$.state` with it, so the plugin also writes a `$.store` mark, `compactionClearMarkKey(hostId)`. The host id is `CLAUDE_CODE_HOST_SESSION_ID`, the desktop's own session id: every process of one desktop session sees it and no other session does, and a terminal host has none and writes no store mark. The mark holds the release and a 10 minute expiry, and is deleted when its start took it or the clear failed. The new process's first start, of any source (`startSeen` is false in a process with no `$.state`, and a `/clear` carries it), reads, takes and deletes only its own session's key. Another session's mark is never touched, and an expired one gives no resume.

A start carrying the mark gets `compactionClear` on its `PendingStart`. `sessionContext` then tells the fresh conversation `session_start`'s text (never a restart notice) followed by the cleared resume briefing (`briefingText(..., 'cleared')`, `CLEAR_RESUME_PROCEDURE`: reload skills, read the newest handoff note, re-read the In Progress cards, continue; no sub-agents line). `resumeAfterCompaction` starts the turn with it for a plan-connected session. A start whose text could not be read, by a throw or by saying nothing, still gets the resume opening (`startEventOf` is the one place that names a start's event). A person's own `/clear` and the ready loop's get none of this.

The spent-release record in `$.store` is `usedReleaseKey(hostId, releaseId)`: `<host id>:<release id>`, or the release id alone when there is no host id. It never uses the engine id, which a clear moves. The dashboard re-sends the same release until `releaseUntilMs`, and a new process after a clear (empty `$.state`, a new engine id that its `session.start` makes the boot id, a relay naming its file by its own id) must read it as spent. The host id keeps two desktop sessions from sharing a record. The guarantee is that one session acts on one release once, and a different release always clears. The newest 40 records stay (`staleReleaseKeys`).

A refused or unproven clear is one toast (`Compaction clear failed: ...`), and the dashboard re-asks once the release expired. Whether the plugin's `/clear` ends the claude.exe process like a desktop clear (DX-7106's measurement) is UNVERIFIED here.

Claude Code keeps `$.store` as one JSON file per plugin (`~/.claude/plugins/store/50arms_50arms-<hash>.json`) and writes it by temp file and rename. ## The 50 Arms plugin carries no `@50arms/platform-mcp` version (DX-4321)

The version is the npm registry's `latest`, recorded in `${CLAUDE_PLUGIN_DATA}/dashboard-mcp/current`. The MCP server launcher (`50arms/scripts/dashboard-mcp-server.mjs`, through `50arms/scripts/lib/dashboard-mcp-package.mjs`) is the one thing that refreshes and installs it:

- Before it starts the server it refreshes the record in a detached child, and waits for that child up to `START_WAIT_MS` (22 s, under Claude Code's 30 s MCP start limit; `DASHBOARD_MCP_START_WAIT_MS` is the tests' seam). The child asks the registry for `latest`, installs it (node, no bash, no shell, into `${CLAUDE_PLUGIN_DATA}/dashboard-mcp/<version>/`; an install already there is skipped) and records it. A session started after a 50 Arms publish therefore runs that publish, with no plugin release (DX-5075: the refresh used to start only after the server, so the first session after a publish ran the version the previous refresh had recorded, one release behind; 0.1.300 predates the advisory dedupe by id and repeated a stored pacing message). The recorded version is installed first if it is not, and with no record the registry's answer is needed to start at all. The registry request is one added round trip on every start, plus the install on the first start after a publish.
- A refresh that settles in time with a new version starts that version. A refresh that fails, or is not done in `START_WAIT_MS`, starts the RECORDED version (installed first if it is not); an unfinished refresh goes on in the background, never restarting the running server, and the next start runs what it recorded.
- A refresh that fails keeps the recorded version and appends one line to `dashboard-mcp/refresh.log`; the next launcher prints that line to its stderr at its start (below).
- Old installs are pruned after the refresh, as a separate step with its own failure line (a prune that fails is never reported as a failed refresh): every staging directory and every version directory over an hour old, except the version this session runs, the recorded one, and any version a live process leases.
- Leases: every process that runs an installed version (the server launcher, and the detached refresh child, which leases the version its launcher ran) writes `<version>/.leases/<pid>` while it runs and removes it at exit, so another session's prune never removes a version a live session runs. A lease whose process is gone (a crash) holds nothing: every prune reads the leases of every version directory, kept and young ones included, and deletes the dead ones.
- **The refresh is a detached child (DX-5314, waited for by DX-5075).** The launcher starts it before the server (`node dashboard-mcp-server.mjs --run-refresh <recorded version>`, node only, no shell, `detached`, `unref`ed after the wait, ALL stdio ignored: it holds none of the launcher's pipes, because the MCP transport may wait for stderr to close) and exits when the server does, without waiting for it or stopping it. A refresh needs about 7 s, and the old in-launcher refresh was aborted silently by every launcher shorter than that (a 2 s probe), so `current` sat three versions behind while only short launchers ran. The child installs into its own staging directory (a fresh `.stage-*` per install), leases the version the launcher ran (`<version>/.leases/<child pid>`) while it works, prunes after it, and appends ONE line to `${CLAUDE_PLUGIN_DATA}/dashboard-mcp/refresh.log` when it fails, times out or is stopped (SIGINT / SIGTERM kill its npm and remove its stage; that clean stop is POSIX-only: on Windows a detached child gets a hard terminate, so its npm and stage are left to the next prune). The NEXT launcher prints the lines in that file to its stderr at start (the file is renamed away first, so none is lost or printed twice): a refresh is never silent, its failure surfaces at the next start. `DASHBOARD_MCP_NPM_CLI` is the tests' seam for npm's CLI (the child is a real process).

No plugin file carries a version literal of the package (a test scans for one).

### A plugin runs beside an older relay (DX-5314)

Claude Code hot-loads every new plugin version into every live session (it writes the session's pid into `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/.in_use/` within the same second for each live session, with no `/reload-plugins`), but a session's MCP relay keeps its version until its MCP server restarts (`/mcp` reconnect, or a new session). Publishing the MCP first, then deploying, then publishing the plugin therefore does NOT protect a live session: it runs the new plugin beside the old relay. DX-5314: plugin 0.15.36 required `valves` in the compaction control file, the sessions' relays (0.1.311 to 0.1.317) wrote none, and every live operator session lost the compaction handshake for hours with only a generic toast. The rule: **a plugin keeps working beside any older relay, degrading only the features the relay cannot feed, with a named notice** (what is off, why, and the fix: reconnect the 50 Arms dashboard MCP server or start a new session). Never read a field an older relay lacks as a corruption that disables a feature the older relay could feed; never fail the whole feature for it. Release order still helps new sessions (publish the MCP and deploy the dashboard before the plugin), but the plugin's own code must not depend on it.

## Publishing is TWO steps, and the second one is not optional

A plugin edit is not shipped until BOTH happen:

1. **Bump + push** — `./scripts/publish.sh <patch|minor|major> <plugin>`. The marketplace loader compares `version` fields, not commit shas; a plain `git push` of plugin source ships nothing to any consumer.
2. **Update this machine's installed records** — `update-claude-plugins` (symlink to `scripts/update-plugins.sh`).

Before any bump, `publish.sh` runs its pre-flights, in this order: the frontmatter lint, the general-audience scan, the hooks-module `claude plugin validate`, the whole suite (`npm test`: the node suites, which hold the rule scans such as `plan-relay-scan` (DX-5201), then `claude plugin test 50arms`, in the test container), and the injection budget. Any one failing refuses the publish with nothing bumped or pushed. The general-audience scan (`scripts/check-general-audience.mjs`) refuses the publish when a shipped skill, agent, hook, script string or the mantra names the author's own setup (a personal account or alias, the author's domain, a card or plan id, a repo path). It reads every shipped file, as its `listPluginFiles` lists them (what `git add <plugin>/` would commit, minus `tests/` and `node_modules/`), with comments in code excluded, and throws on a file type it does not know, so teach it a new type before shipping one.

Step 2 exists because **installed plugin versions are recorded PER PROJECT** in `~/.claude/plugins/installed_plugins.json`. Pushing a new version makes it *available*; nothing moves a project's record onto it. Claude Code's own auto-update cannot do it here: the desktop app launches its CLI with `DISABLE_AUTOUPDATER=1`, which the docs state disables automatic updates "for both Claude Code and all plugins".

The failure is silent and uneven, which is why it went unnoticed for two months: the `50arms` project sat on `base` v0.3.15 (June 9) and `50arms` v0.3.65 while the `platform` project on the same machine ran v0.3.27 and v0.3.113. Every session looked healthy while loading two-month-old skills, rules, and hooks.

## MANDATORY — run `update-claude-plugins` after ANY plugin push

`publish.sh` already calls it automatically after a successful push, so the normal flow needs no extra command. **Run it by hand whenever a plugin's content reached `origin/main` by any other route:**

- a plain `git push` of plugin source (no bump — fix that first, then update)
- a push from another machine, a dispatched worker, or the GitHub web UI
- a `git pull` that brought someone else's plugin bump into this machine's clone
- any time you are unsure whether this machine's records match `origin/main`

It updates **every plugin in every project on this machine** in one command — there is no per-repo invocation. It is idempotent and skips rows that are already current, so running it when nothing changed costs a few seconds and prints "already current". Running it unnecessarily is free; skipping it leaves projects silently stale.

```bash
update-claude-plugins            # sweep every project on this machine
update-claude-plugins --dry-run  # show what would be checked, change nothing
```

Updates apply to the NEXT session — a running session keeps the versions it loaded at launch. That is Claude Code's own model, not a limitation of the script.

A `SessionStart` hook in `~/.claude/settings.json` also runs it asynchronously with a 6h throttle. Treat that as a backstop, not the mechanism: as of 2026-08-13 the hook is wired but has NOT been observed firing.

## Mechanical pre-action check

Before declaring any plugin work done, answer both:

1. Did `./scripts/publish.sh <bump> <plugin>` run and push? No → the edit is unshipped.
2. Did `update-claude-plugins` run after that push (or did `publish.sh` run it for you)? No → this machine is still loading the old version.

"I'll update later" / "the consumer will pick it up" / "it's only a small edit" are the rationalizations both checks exist to block.

Both yes → done. **NEVER test, verify, or file AC or problems about the published version reaching or loading in a new session** (operator, 2026-09-27) — that is the Claude Code harness's job, it works, and it is not ours.
